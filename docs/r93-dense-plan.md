## 1. Why this shape (recon + derivation)

### 1.1 How the repo builds/accounts an aligned model

- `tools/make_aligned_config.py` writes the aligned-schema config (`engine_config` +
  `aligned_spec` + `accounting`). `--dense-h H` builds patch-P6 `DenseFFN` (plain SwiGLU, no
  router/gate) instead of MoE. The generator instantiates the real model (`account()`) → torch
  required → run it **on the GPU box** for authoritative numbers; on the Mac we use the analytic
  identity below (validated to 0.005%) and re-check on the instance during prep.
- `tools/aligned_build.py::install_aligned(path)` registers the config JSON at runtime
  (`CONFIGS[name]` + `ENGRAM_PRESETS[name]`), so `p2_train.py --config-json <path>` works without
  editing `nanov41/configs.py`. `--engram auto/ON` is the default when the config has an `engram`
  section; `--engram none` turns it off.
- `p2_train.py` takes `fwd_flops_per_token` from `accounting.fwd_flops_per_token_est` and reports
  raw MFU = 3·fwd·tokens/s / 209.5 TF.

### 1.2 The accounting convention (repo-wide, reuse exactly)

```
N_active        = (backbone non-embedding params) + (head params = V*dim)
fwd_flops/token = 2 * N_active                       # embed lookup counts 0 FLOPs
C               = 3 * fwd_flops * D = 6 * N_active * D
```
For a **dense** config (no router, no expert capacity):
```
body_non_emb = non_ffn(dim, layers) + layers * 3 * dim * dense_h
non_ffn      = attention core (wq_a/q_norm/wq_b/wkv/kv_norm/wo_a/wo_b + attn_sink)
             + attn_norm + ffn_norm
             + mHC (hc_mult=4): 2 * [ (2+hc)*hc * (hc*dim) ] + 2*(2+hc)*hc + 2*3
             + Compressor (layers in kv_source_layers): head_dim + dim*head_dim (+ dim*head_dim if ratio>1)
             + Indexer   (layers in index_source_layers): q_lora*(idx_nh*idx_hd) + dim*idx_nh
                                                          + head_dim*idx_hd + idx_hd (owns_k)
```
with `n_heads=dim/64, head_dim=64, q_lora=round16(dim/4), o_lora=round64(dim/5),
o_groups=min(8,n_heads), index_n_heads=n_heads/2, index_head_dim=16`, and the compress-ratio /
KV-source pattern generated by `make_aligned_config.build_engine_config` (modes='ratio').
The MoE **router gate** params are *not* counted for dense (the committed
`make_arch_twins.py::DENSE_OTHER` constant was derived from the MoE config and includes the gate —
that is the only difference; we recompute without it).

Validation (`tools/r93_make_configs.py::validate_identity`, runs on every invocation):
d12/dim512 analytic 10,359,944 vs 10,360,456 derived; d16/dim640 17,876,896 vs 17,877,536;
d20/dim640 22,306,848 vs 22,307,488 → Δ ≤ 640 params (≤0.005%).

d24_c1 full accounting: body_non_emb 245,706,032 (non_ffn 75,836,720 + FFN 169,869,312) +
head 42,270,720 = N_act 287,976,752; embed 42,270,720; backbone 330,247,472; +Engram
220,049,152 = **550,296,624** stored params. Engram wkv is real compute but excluded by the

3-matrix SwiGLU) lands at the same N_act. Deeper/wider alternatives are costed above; d24_c1 is
the balanced choice, d16w_c2 the memory/MFU-friendlier backup.

## 2. Engram ON with the K=40k tokenizer (C40 patch — required)

`nano_engram.apply_preset()` hardcodes `DEFAULT_COMPRESSED_VOCAB_SIZE = 99,092` and
`ref/engram.py::NgramHashState.__init__` asserts
`build_compressed_token_map(tokenizer).size == args.engram_compressed_vocab_size`.
`build_compressed_token_map` decodes every token, normalizes (NFKC→NFD→strip accents→lowercase→
collapse whitespace→strip) and counts distinct keys. For the K=40k tokenizer
(`runs/r92/vocab/K40000_s1280/tokenizer.json`, V=41,280) that count is **C40 = 32,410**
(952 partial-byte tokens; verified with `tokenizers 0.22.1`: the identical code reproduces
**99,092** for the official 129k tokenizer, matching the hardcoded constant).

Fix (no shared-file edits): `tools/r93_p0b_train.py` wraps `p2_train.main()` in-process, computes
C40 through the model's own code path (`ne.install()` + `load_tokenizer_adapter` +
`build_compressed_token_map`), sets `ne.DEFAULT_COMPRESSED_VOCAB_SIZE = C40`, then runs p2_train.
Table prime/row geometry is unchanged and still valid: hash ids are
`(compressed_id * multiplier xor …) % prime + offset` and C40 < every bucket size → every id lands
inside its table. The checkpoint stores cfg with C40, so eval rebuilds the same hash map
(`nanov41.eval.provider.ModelProvider` reads `NANOV41_DS_TOKENIZER_JSON` and the ckpt cfg —
no patch needed at eval time).
Prep cross-checks: exact C40 (31,xxx… from `--compute-c40`) vs pure-python estimate
`tools/r93_engram_c40.py` (32,553, +0.4%) — **the exact value is authoritative and is what the
runner uses**; prep asserts it equals the stamped value (expected 32,410).
Fallback if the patch path ever breaks: `--engram none` ablation (R91 showed Engram is worth
−0.05…−0.10 bpb at these scales, so this is a labelled ablation, not a valid P1 config).

## 3. Target math and gates

bpb interpolation line (R90/R91; two anchors: production 1.2006 @4.12e18, nanochat 0.748 @4.33e19):
```
bpb_pred(C) = 0.748 * (C/4.33e19) ** -0.20      with C = 3 * fwd_flops * D
```
- bpb = 1.0 ⇔ **C = 1.014e19**; for d24_c1 that is D = **5.87B tokens**.
- P1: D = 6.0B ⇒ C = 6·287,976,752·6.0e9 = **1.0368e19** ⇒ **bpb_pred 0.9956** (<1.0).
- P0b gates (d24_c1, fwd 575.95M):

| D tokens | C | bpb_pred |
|---|---:|---:|
| 0.2B | 3.456e17 | 1.9656 |
| 0.4B | 6.911e17 | 1.7111 |
| **0.6B** | 1.0368e18 | **1.5780** |
| 0.8B | 1.382e18 | 1.4903 |
| 5.8B | 1.0022e19 | 1.0023 |
| 6.0B | 1.0368e19 | 0.9956 |

Gate interpretation: the line carries ±2× FLOPs uncertainty (γ≈0.20 from 2 anchors) → ±0.05 bpb is
a health band, not a precise prediction. A WSD run's **0.2/0.4B checkpoints are mid-stable-phase
(no cooldown)** and read a few 0.01–0.06 bpb ABOVE the line at that budget; **only the final
cooldown point is the gate**.

## 5. LR math

R91 measured dense LR law (v41 Muon peak LR; `runs/r91/c/lr_law.json`):
`lr* = 10^-2.732944 · D^-0.27016` at **tok/step 1.048576M, dim 512** (fitted
lr* = 5.927e-3 @100.7M, 4.405e-3 @302.0M; 2-point fit, low confidence). Convert to our shape:
`× sqrt(512/dim)` (μP width) and `× sqrt(tok_per_step/1.048576e6)` (lr* ∝ batch^0.5).

- **P0b LR (D=0.6B, tok/step 2^21, dim 1024)**:
  `4.405e-3 × (0.6/0.30199)^-0.27016 × sqrt(512/1024) × sqrt(2)` = 4.405e-3 × 0.8307 × 0.7071 ×
  1.4142 = **3.66e-3**. The runner uses the approved **2.9e-3** (conservative; R91's dense bpb curve
  is flat near the optimum — at 302M, ±25% LR moved bpb by ≤0.004 — so 2.9e-3 costs ≲0.005 bpb vs
  optimum and stays on the safe side for stability).
- **P1 LR (D=6.0B, tok/step 2^21, dim 1024)**: same formula → 4.405e-3 × (6.0/0.30199)^-0.27016 ×
  0.7071 × 1.4142 = **1.96e-3** (high end; width and batch factors cancel exactly). Independent
  long-horizon prior (production-anchored laws, a≈−0.35…−0.53, validated on the 7.5B run within 5%)
  gives **6.3–6.9e-4** (low end). Recommend **1.0e-3 central, range 0.6–2.0e-3**, and a 3-arm LR
  mini-sweep (e.g. 0.6/1.0/1.7e-3 × ~0.5B tokens ≈ 3×3.5h ≈ ¥29… or 2 arms at 0.3B ≈ ¥12) before
  the 6B commit. Do not copy P0b's short-run LR to P1 (R91 learning #2: short-run optimum is
  4–8× too high for long runs).

## 7. Fallbacks and risk register

| risk | probability | mitigation |
|---|---|---|
| production fast kernels assume dim 512 (TL attn v3 / mHC v4 / ew fusion / linear-fp8 at new shapes) | medium | smoke (20M tokens) is the first thing that runs; on failure retry with the dense-generic env (unset the fast-path envs → torch fallbacks, slower); Plan-C native dim512 shape documented above |

| b2×s8192 activation memory OOM (estimated ~12 GB + ~6 GB params/opt) | low-medium | smoke falls back to b1×s8192×accum256 (same tok/step); runner records both |
| hf-mirror slow/断流 | medium | prep has curl -C - resume, 3 retries, size checks, 4 parallel connections; 18th shard optional |
| Engram C40 patch breaks (assert/NaN) | low | prep asserts C40; smoke checks loss; fallback `--engram none` ablation |
| P0b bpb > gate+0.05 | low | that IS the calibration signal: report as FAIL with diagnosis (LR/recipe/line uncertainty), do not silently retry |
| over budget | low | runner projects tokens from smoke tok/s, reserves prep+eval, watchdog hard-stops at ¥19 |

## 11. P1 预期 vs nanochat 0.718：差距归因与预算建议（2026-11-16，HP 搜索后）

### 11.1 口径对照

| | nanochat d24（0.748 锚点） | P1 8B（d24_c1 dense） |
|---|---|---|
| 模型 | dense 730M non-embedding（1.38B 总，dim 1536，24L） | dense 288M active（dim 1024，24L，Engram 220M） |
| tokens | 8.758B | 8B |
| tokens/param | 12 | 27.8（更“过训练”） |
| FLOPs/token | 4.94 GFLOP | 1.73 GFLOP（2.86× 更低） |
| 总训练 FLOPs | 4.33e19 | **1.38e19（32%）** |
| 实测 bpb | 0.748；leaderboard best **0.718** | **预测 0.89**（区间 0.85–0.96） |

### 11.2 差距分解（0.89 → 0.718 的 0.17 bpb）

| 因素 | 量级 | 说明 |
|---|---|---|
| ① 总算力 | **3.1×** | 仓库插值线上 1.38e19 处的“应有” bpb = **0.94**；我们预测 0.89 → **等 FLOPs 下领先 ~0.05**；0.06–0.08 的差距就是 3.1^0.2 买不回来的预算 |
| ② 模型容量 | **2.5× 参数** | 同 token 数 bpb∝N^-0.34：730M→288M 约值 0.08–0.12；nanochat 是“大模型×少 token”，我们是“小模型×多 token” |
| ③ 数据配方 | 0.02–0.05 | 0.718 来自 ClimbMix GPT-2-capability 150-shard 子集 + 其配比；P0b 语料是纯 web 随机子集 |
| ④ 训练技巧缺失 | 0.03–0.06 | EMA（0.015–0.017）、z-loss、LR 校准（S1 实测 P0b 的 2.9e-3 偏高 ~40%）、cooldown 形状、data ordering |
| ⑤ tokenizer/context | ±0.01 | K=40k = 4.4426 B/token（nanochat 32k ≈4.0–4.2）略占优；8192 context 略占优 |
| ⑥ 评测口径 | ±0.01 | 3M/5M 子集、window 2048 等 |

结论：**0.17 bpb 差距 ≈ 0.13（算力/容量，即预算）+ 0.04（数据/技巧）**。与
`docs/scaling-learnings.md` §8 的旧结论一致：容量/数据配比而非训练实现是主要差距。

### 11.3 打到 0.718 的路线与费用（单卡 5090 @62.8k tok/s，¥13.2/B tokens）

| 路线 | 规模 | 预计 bpb | 时间 | ≈费用 |
|---|---|---|---:|---:|
| ① 同架构堆 token | d24_c1 × **30B tokens** | ~0.72 | 136 h | **¥405** |
| ② **放大模型（推荐）** | ~600–730M active × 9–10B tokens（C≈3.6–4.4e19） | **0.74–0.79** | 92–98 h | **¥275–292** |
| ③ ②+KD（−5.2%） | 同上 | **0.72–0.75** | 92 h | ¥280 + KD 数据 |
| ④ ①+KD | d24_c1 × ~21B | ~0.72 | 93 h | ¥277 |

要点：**堆 token 不划算**（d24_c1 到 30B 已是 104 tok/param，边际很小）；**放大模型到
~600–730M active 在 iso-FLOPs 下更便宜也更低**（与 R91 容量曲线“¥420 → ~600M × 12B”一致）。
nanochat 的 0.718 自身 ≈¥285（8×H100 list），**单卡 5090 追绝对 bpb 没有成本优势**；我们的优势是
等 FLOPs 下低 ~0.05 bpb → **P1 8B（¥106，0.89 vs 线 0.94）是“性价比超 nanochat”的里程碑**，
绝对 0.718 是 P2 预算（¥280–405）。

### 11.4 P1 配方更新（HP 搜索结果，`docs/r93-hp-search-results.md`）

- **峰值 LR：0.7–1.0e-3**（S1 实测：0.2B 顶点 3.77e-3、0.4B 顶点 2.03e-3，短跑最优随步数快速下降；
  R91 定律的 1.8e-3 **不可用**；产线先验 0.63–0.69e-3 作为下沿）。
- **tokens/step**：**2^21**（S3 完整 2×2：2^22 即使 LR×√2 也 +0.138 bpb，batch 翻倍不免费）。
- **z-loss**：S2 实测 0.3B 上 Δbpb=−0.005（低于 0.01 阈值）但 +17.7% 吞吐；P1 可选
  “不启用+监控 head norm”或“先实现快速路径 z-loss 再用”，见 `docs/r93-hp-search-results.md` §3。
- **EMA**：P1 前实现（预计 0.015–0.017 bpb，白拿）。
- **bpb 预期**：8B 中心 0.89（0.85–0.96）；落地 EMA+LR 校准后 **0.84–0.87**；
  `loss = 3.0856 × bpb` → 8B ≈2.75 nats/token（EMA 后 ~2.6–2.7）。
