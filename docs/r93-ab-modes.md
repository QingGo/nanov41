## 1. What was tested

Our P1 main-run config `d24_c1` uses CSA2 with the official **compression ratios** (m=2 encoder half,
m=1 decoder half) but **one reuse group per half**: `kv_source_layers=[1,12]`,
`index_source_layers=[1,12]` → 2 Full layers, 0 Reindex. The official V4.1-Flash pattern is encoder
groups of **6** layers (Full+5 Reuse) and decoder groups of **4** layers (group 1 Full, groups 2+
**Reindex**; index sources 24/28/32/36 of 40).

| field | base arm | ced arm |
|---|---|---|
| layer modes | `swa, full, reuse×10, full, reuse×11` | `swa, full, reuse×5, full, reuse×4, full, reuse×3, reindex, reuse×3, reindex, reuse×3` |
| compress_ratios | `[0, 2×11, 1×12]` | identical (compression ratios unchanged) |
| kv_source_layers (Full) | `[1, 12]` | `[1, 7, 12]` |
| index_source_layers | `[1, 12]` | `[1, 7, 12, 16, 20]` (16/20 = Reindex) |
| active params | 287,976,752 | 288,231,808 (+0.089%) |
| fwd FLOPs/token (repo convention) | 575,953,504 | 576,463,616 (+0.089%) |
| real fwd FLOPs/token (incl. CSA2) | 579,660,384 | 585,923,328 (+1.08%) |
| everything else (dim/FFN/Engram C40/vocab/seq/precision env) | identical | identical |

Generated by `tools/r93_official_modes.py` (CPU-only). The engine (`ref/model.py`) implements
Full/Reuse/Reindex natively through the two source lists, so this was a config-only architecture
change; it required no kernel work. Gotcha found during setup: `layer_modes` must **not** inside
`engine_config` (`ModelArgs(**cfg)` rejects unknown keys) — it lives at the JSON top level.

## 3. Why the official pattern is slower than its FLOP share (important lesson)

+1.08% "real FLOPs" turned into **+6.9% wall**. The CSA2 machinery is **not** GEMM-dominated:
each added Full/Reindex layer runs a compressor projection plus an indexer Q/score pass over the
compressed KV (for ratio-1 decoder layers: 8192 positions/token), which is a small-N,
gather-heavy, bandwidth-bound workload — its cost per FLOP is several× the dense-GEMM average.
Two added Reindex layers + one added encoder Full layer therefore cost ~7% wall while adding ~1% FLOPs.
(Also consistent with the measured bucket structure: only ~38% of the d24 replay is bf16 GEMM;
the rest is elementwise/attention/EW where the indexer lives.)

## 4. Why the quality did not improve at this scale

- Official group sizes (6/4) are tuned for a 40-layer, 5120-dim, 129k-vocab, 64K→1M-context MoE;
  at d24/8k/41k-vocab the compressed-KV pool per group is only 8192·ratio positions and the
  cross-layer reuse distance (1 vs 5-11 layers) is a much smaller effect than at long context.
- The ced arm also spends its extra compute on indexer refreshes rather than on model capacity
  (+0.089% params only), so there is no offsetting capacity gain.
- Caveat: a 0.3B-token, seq-8192 A/B cannot rule out a benefit at **long context** (32K+) or at
  larger width/depth; if the P1 line later goes >16K context, re-test the Reindex/grouping question
  then, with the long-context eval as the criterion (and note the +7% wall budget).

  base arm is therefore a usable independent replication of both P0b throughput and curve; keep P1
  extrapolations anchored to measured points, not the analytic line.
